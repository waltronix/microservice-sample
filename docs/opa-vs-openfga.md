## Overview

| | OPA (Open Policy Agent) | OpenFGA |
|---|---|---|
| **Model** | Policy-as-code (Rego) | Relationship-based (ReBAC) |
| **Authorization style** | Attribute-based (ABAC) / Role-based (RBAC) | Fine-grained relationship graphs |
| **Data source** | Policy + external data bundle | Relationship tuples stored in its own DB |
| **Query type** | Arbitrary policy evaluation | `check(user, relation, object)` |
| **Language** | Rego (declarative logic) | DSL (`.fga` model) + API |
| **Origin** | CNCF graduated project (Styra) | Based on [Google Zanzibar](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/), open-sourced by Auth0/Okta |
| **Storage** | Stateless — data pushed in or fetched at eval time | Stateful — owns its tuple store |

## How Each Works

### OPA

[OPA](https://www.openpolicyagent.org/) evaluates **[Rego](https://www.openpolicyagent.org/docs/latest/policy-language/) policies** against an **input document** and optional **data documents**. Policies are arbitrary logic: boolean decisions, structured results, partial evaluation. OPA itself is stateless — it holds no persistent state beyond the loaded policy and data bundle. Data reaches OPA either via a bundle pushed at startup or by OPA pulling it from a bundle server at query time.

A typical query looks like:

```
POST /v1/data/library/authz/allow
{ "input": { "user": "user:alice", "relation": "reader", "object": "book:123" } }
```

The Rego policy walks the data document to resolve the decision. In this project, `OpaClient::write_tuple` populates `data.library.tuples` and the policy in [libraries/authz/opa/library.rego](../libraries/authz/opa/library.rego) manually encodes the `owner ⊆ writer ⊆ reader` hierarchy using explicit rules.

### OpenFGA

[OpenFGA](https://openfga.dev/) models authorization as a **graph of typed relationships** between users and objects. The model (`.fga` file) declares object types and their relations. Tuples — `(user, relation, object)` triples — are written to OpenFGA's database at runtime. At check time, OpenFGA traverses the graph automatically, following relation hierarchies declared in the model.

A check looks like:

```
POST /stores/{store}/check
{ "tuple_key": { "user": "user:alice", "relation": "reader", "object": "book:123" } }
```

The model in [libraries/authz/fga/model.fga](../libraries/authz/fga/model.fga) declares `reader: [user, group#member] or writer` and OpenFGA resolves that transitivity itself — no custom logic needed.

## Technical Differences

### Policy logic vs. graph traversal

OPA puts the intelligence in the policy. You write Rego rules that encode every permission derivation. This gives you full expressivity — you can write arbitrary logic, inspect JWT claims, cross-reference external data, or compute decisions based on time, environment, or request attributes. The trade-off is that you own all the graph-traversal logic. In `library.rego`, the `owner ⊆ writer ⊆ reader` chain and group membership expansion are explicit rules, and they must be kept in sync with the data model manually.

OpenFGA puts the intelligence in the model. The `.fga` schema encodes the hierarchy once, and OpenFGA handles traversal for every check. You cannot embed arbitrary logic; the model is declarative and type-safe. If you need a rule like "writers can read only if the book was published before their account was created," OpenFGA cannot express it — OPA can.

### Statefulness

OPA is **stateless** at the policy engine level. Data must be loaded in ahead of evaluation — either embedded in the policy bundle or pushed via the data API. In this project, `OpaClient::write_tuple` writes tuples into OPA's in-memory data store over the REST API. This is convenient for small datasets but means OPA has no durable storage of its own: on restart, all data must be re-loaded.

OpenFGA is **stateful**. It owns a PostgreSQL (or other) database that persists tuples across restarts. Writes are durable. This makes it the natural fit when the authorization data is itself a first-class domain concern that changes at runtime (e.g., sharing a document with a new user).

### Consistency and scale

Because OPA is stateless and data is typically bundled, it is easy to run many replicas with eventual consistency (bundles are refreshed on a timer). For read-heavy policy evaluation at high request rates, OPA scales horizontally with no coordination overhead.

OpenFGA's database introduces a consistency boundary. Auth0's hosted version provides "eventual consistency" with Zookies (consistency tokens, mirroring Zanzibar's design) to handle replication lag. Self-hosted OpenFGA inherits the consistency guarantees of its backing store.

### Testing

OPA ships with `opa test` — you write `_test.rego` files that live alongside the policy (see [libraries/authz/opa/library_test.rego](../libraries/authz/opa/library_test.rego)). Policy unit tests run without any external service.

OpenFGA's model can be validated with the `fga` CLI and its own test format. Integration tests require a running OpenFGA instance (the BDD tests in [tests/authz-bdd/](../tests/authz-bdd/) use testcontainers to spin up both OPA and OpenFGA).

## When to Choose OPA

- **Complex, context-rich policies.** Decisions depend on request attributes (HTTP method, path, query parameters), JWT claims, time-of-day, resource metadata, or any data you can load into OPA's data document.
- **Multi-layer policy enforcement.** OPA integrates with Kubernetes admission control, Envoy external authorization, Terraform plan checking, and CI/CD gates. It is not just a microservice auth layer.
- **Auditable, version-controlled policy.** Rego policies live in git, are testable with `opa test`, and can be deployed through standard CI pipelines. The policy is code.
- **No persistent state required.** Your authorization rules are derived from identity + resource attributes that already exist elsewhere, with no need to store explicit relationship tuples.
- **Mixed RBAC + ABAC.** You need role-based access combined with attribute conditions ("admins can delete only their own tenant's data").

**Examples:** API gateway authorization, Kubernetes RBAC extension, infrastructure policy (Terraform), data pipeline row-level security.

---

## When to Choose OpenFGA

- **Fine-grained object-level sharing.** Users grant access to specific resources to specific people — the Google Docs model. Relationships are dynamic and user-driven.
- **Deep relation hierarchies.** Access propagates through object hierarchies (a user with access to a folder has access to all files in it, recursively). Writing this traversal manually in Rego becomes error-prone at scale.
- **Relationship data is first-class.** Who can access what is itself domain data, written and read like any other persistent record. It needs to survive restarts and be queryable ("list all objects user X can read").
- **Reverse lookups.** OpenFGA supports `ListObjects` and `ListUsers` — answering "what can this user access?" or "who can access this object?" without a full table scan. OPA has no equivalent built-in.
- **Decoupled from the service.** Authorization data (the tuples) is managed separately from policy, which is useful when non-engineers (e.g., product or ops) need to manage sharing rules through a UI backed by the OpenFGA API.

**Examples:** Document sharing (Google Docs, Dropbox), project/org permission trees (GitHub repos, Linear teams), SaaS multi-tenant resource ownership, any "resource-centric" sharing model.

## Side-by-Side in This Project

This project implements both backends behind the shared [`AuthzBackend`](../libraries/authz/src/backend.rs) trait, making the difference concrete.

**OpenFGA** — the model does the work:

```fga
type book
  relations
    define owner: [user]
    define writer: [user, group#member] or owner   // owner implies writer
    define reader: [user, group#member] or writer  // writer implies reader
```

A single `check(user:alice, reader, book:123)` traverses the full graph automatically.

**OPA** — the policy does the work:

```rego
allow if has_tuple(input.user, input.relation, input.object)

allow if {
    input.relation == "reader"
    has_tuple(input.user, "writer", input.object)   // writer implies reader — manual
}

allow if {
    input.relation == "reader"
    has_tuple(input.user, "owner", input.object)    // owner implies reader — manual
}
```

Each implication is an explicit Rego rule. For this domain, it is manageable. For a hierarchy with six levels and conditional overrides, OPA rules grow substantially while the OpenFGA model stays flat.

## Summary

| Criteria | OPA | OpenFGA |
|---|---|---|
| Authorization model | ABAC / RBAC + arbitrary logic | ReBAC (relationship graph) |
| Policy expression | Rego (code) | Typed relation model (DSL) |
| Hierarchy traversal | Manual (you write it) | Automatic |
| Stateful tuple storage | No (push data in at runtime) | Yes (owns its DB) |
| Reverse lookups | No built-in | Yes (`ListObjects`, `ListUsers`) |
| Context-rich decisions | Excellent | Limited to relation graph |
| Multi-system enforcement | Excellent (k8s, envoy, TF, CI) | API-only |
| Testing | `opa test` (unit, no service) | CLI + integration test |
| Best fit | Policy-as-code across the stack | Object-level sharing at scale |

Choose **OPA** when authorization is policy logic applied to rich request/resource context. Choose **OpenFGA** when authorization is a relationship graph where users explicitly share access to specific objects.
